# 01 · 项目概述与产品定位

## 1. 为什么要做这个产品

高考志愿填报是一个「低频、高 stakes、信息极度不对称」的决策场景。项目初期调研归纳出三个核心痛点，并以此作为产品设计的出发点：

| 痛点 | 具体表现 | 对产品的要求 |
|---|---|---|
| 信息极度不对称且动态变化 | 录取规则受省份、选科、招生政策、计划变动影响，年年在变 | 数据必须可溯源、可更新，推荐逻辑要适应不同投档模式 |
| 产品同质化严重 | 多数竞品停留在「分数线大数据匹配」，只给分数不给解释 | 推荐结果要可解释，让考生知道「为什么这个能冲、那个必须保」 |
| 用户容错率极低 | 滑档或被调剂到不接受的专业，影响深远 | 必须有风险诊断与梯度兜底，不能只给一份「最优解」 |

## 2. 差异化方案选型

调研阶段产出过四套候选方案：

- **方案 A · 确定性推荐引擎**：数据溯源 + 动态风险预警 + 五步透明推荐 + 政策 RAG 解析。
- **方案 B · 家庭共识平台**：考生 / 家长双端、分歧可视化、家庭共识书。
- **方案 C · 生涯导航**：以职业规划反向倒推专业与院校。
- **方案 D · AI 沙盘推演**：对话式模拟不同填报策略的结果。

**最终选择 A × B 组合切入**：用 A 的「可解释推荐 + 风险预警」作为差异化敲门砖，用 B 的家庭共识思路提升留存。C / D 作为后续演进方向，未纳入 MVP。

> 说明：以上为产品规划层的决策依据。B 方案中的「家庭双端」「共识书」、A 方案中的「政策 RAG 引擎」属于规划，**当前仓库未实现**，详见 [10 · 实现边界与后续规划](10-实现边界与后续规划.md)。

## 3. MVP 实际收敛范围

产品规划文档给出的构想很宽，但代码实际落地的是一条完整可用的主链路：

```
分步采集考生信息
  → 位次自动换算
  → 偏好与权重输入
  → 四梯度志愿推荐（数据库筛选 + LLM 排序）
  → 录取风险诊断
  → 结果页展示
```

围绕这条主链路，配套实现了：

- 邮箱验证码注册 / 登录 / 会话管理
- 省份、选科、批次线、选科覆盖率的查询接口
- 前后端数据解耦（静态配置 JSON + 动态接口）
- 本地一键启动脚本、Docker 部署配置、GitHub Pages 自动构建

## 4. 用户画像与核心使用场景

**主要用户**：应届考生（18 岁左右）及其家长。

**典型场景**：出分后的 72 小时内，需要在信息不完整、时间紧迫、情绪紧张的状态下，从数百个院校专业组中筛出一份「冲得上、录得到、不后悔」的志愿表。产品要解决的是「引导用户无痛输入信息」和「给出高容错率的推荐」两件事：

- 前者靠分步式 Wizard 表单 + 系统自动反查位次来降低填写负担；
- 后者靠四梯度分配 + 风险诊断 + 黑名单拦截来降低决策失误概率。

## 5. 产品与工程的对应关系

| 产品诉求 | 工程实现 | 状态 |
|---|---|---|
| 无痛输入信息 | 分步表单 Wizard，位次由分数自动反查 | 已实现 |
| 选科合法性校验 | 3+3 / 3+1+2 组合规则校验与错误码 | 规则已定义；前端校验部分已实现 |
| 高容错率推荐 | 冲 / 稳 / 保 / 垫四梯度，每档 2 条共 8 条 | 已实现 |
| 可解释推荐 | LLM 生成每条 ≤30 字推荐理由 + 专业匹配度 purity | 已实现 |
| 风险预警 | POST /api/risk 返回 6 项诊断 | 已实现 |
| 数据可溯源 | 批次线 / 位次段 / 选科覆盖表均带 source 字段 | 已实现 |
| 政策 RAG 解析 | — | 设计中，未实现 |
| 家庭双端共识 | — | 设计中，未实现 |
