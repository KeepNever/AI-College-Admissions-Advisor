## 4. 容量规划数字（📐，非实测）

流量模型文档做过推演，以下数字**是设计目标，不是压测结果**：

| 指标 | 估算目标 | 出处 |
|---|---|---|
| 峰值 QPS | ≥10000（上限 15000） | traffic-model-analysis-v1.md |
| 出分日总请求 | 895 万 / 日 | 同上 |
| 读写比 | 92:8 | 同上 |
| 推荐响应 P95 / P99 | <500ms / <1s | 同上 + 后端架构文档 |
| 查询响应 P95 | <200ms | 同上 |
| SLA | ≥99.9% | 后端架构文档 |
| 注册用户 / 活跃 | 30 万 / 24 万 | 流量模型 |
| 实例扩缩容 | 日常 2-4 → 峰值 20-50 | 后端架构文档 |

**项目未做高并发压测。** 面试被问到时请直接说明：这些是容量规划阶段的目标值，验证需要真实流量环境。

## 5. 已知技术债

1. **数据覆盖有限**：真实数据为样本规模，全量院校 / 专业 / 计划需持续导入。
2. **趋势推断简化**：`inferTrend()` 当前固定返回 `stable`，历年涨跌趋势未做真实计算（候选里的三年分数为基于最低分的估算值）。
3. **选科校验不完整**：PRD 定义的完整组合校验矩阵尚未全部编码进后端接口。
4. **推荐理由依赖 LLM**：理由质量依赖模型输出，未做量化评估；降级时用固定文案。
5. **文档与源码不同步**：早期后端 README 的「后续扩展点」仍写着「加入缓存、位次直查、JWT 鉴权、限流」，其中位次直查和 JWT 已实现。本仓库文档已统一按源码重写。

## 6. 后续规划（建议优先级）

| 优先级 | 事项 | 理由 |
|---|---|---|
| P0 | 补齐全量真实数据（31 省、院校、招生计划） | 推荐质量的根本 |
| P0 | 选科完整校验矩阵落地 | 直接关系志愿有效性 |
| P1 | 真实趋势计算（基于多年分数序列） | 提升推荐可信度 |
| P1 | Redis 缓存热点位次映射与推荐结果 | 降低重复请求延迟与 LLM 成本 |
| P2 | 限流 / 熔断 / 健康检查完善 | 应对出分日峰值 |
| P2 | 政策 RAG 问答 | 差异化卖点 |
| P3 | 家庭共识 / 志愿表导出 / 微信登录 | 产品扩展 |
