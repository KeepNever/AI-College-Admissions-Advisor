**AI 高考志愿填报助手**｜全栈开发　2026.06

### 详版（适合项目深挖环节，按 STAR 组织）

**项目背景**：高考志愿填报信息不对称、同质化严重、容错率极低。目标是用可解释的智能推荐 + 风险诊断，帮考生在高压力下产出一份高容错率的志愿方案。

**职责**：独立完成产品调研、PRD、前后端开发、数据导入、测试与部署全流程。

**关键工作**：
1. **推荐引擎重构**：将早期「线差法 + LLM 自由生成」升级为两步法。用位次（跨年份更稳定）替代分数做锚点，数据库负责事实检索，LLM 负责判断与解释；设计四级降级策略，保证任何单点故障不影响结果返回。
2. **数据工程**：编写 8 个导入脚本与约 32KB 的 Markdown 解析器，把录取分数、招生计划、批次线、一分一段等源数据清洗入库；用联合唯一约束防重复导入，用 source 字段保证可溯源。
3. **前后端解耦**：把散落的硬编码数据拆成静态 JSON 配置与动态接口两层，逐项验证「改配置前端即变」，实现前后端并行开发。
4. **质量保障**：用 Vitest + Supertest 覆盖认证链路；两轮 QA 拦截并修复两个真实 Bug，真实数据抽样核对与源数据一致。

**结果**：一条从信息采集到志愿推荐、风险诊断的完整链路可用；具备本地一键启动、Docker 生产部署与 CI 自动构建能力。

## 3. 高频面试问答

**Q1：为什么用位次而不是分数做推荐？**
分数每年难度不同、含金量不同，同一分数在不同年份对应的位次差别可能很大；而录取本质是省内排名竞争，位次是跨年可比性更强的锚点。所以用分数通过一分一段表换算成位次，再基于院校历年最低位次做匹配。位次映射表带 `sameScore`、`rangeMin`、`rangeMax`，能反映同分人数区间。

**Q2：大模型在这个项目里到底做了什么？为什么不让它直接推荐？**
LLM 只做三件事：对数据库筛出的候选集排序、给每个志愿打「专业匹配度 purity」分、写不超过 30 字的推荐理由。不让它直接生成院校名单和分数，是因为模型会编造不存在的数据（幻觉），事实数据必须由数据库保证。这样也把输入 Token 控制在很小的候选集内。

**Q3：LLM 挂了怎么办？**
三级降级：没配 API Key 就不注入 LlmService，直接数据库排序；调用超时或异常就捕获并按位次差排序、purity 默认 70、理由用固定文案；数据库也没候选就返回空数组并记告警日志，不会让前端白屏。城市偏好过滤后不足 4 条候选时也会保留全量兜底。

**Q4：数据库为什么分三个 Schema？怎么防止数据重复导入？**
分 app（应用数据）、data（基础数据）、rec（位次映射）三个 Schema，便于按变动频率分别管理和备份。防重复靠联合唯一约束：录取数据和招生计划都用 `[provinceCode, year, universityId, majorId, batch]` 做唯一键，重复导入会直接失败。

**Q5：选科校验怎么做？**
定义了传统文理、3+3、3+1+2 三套规则。3+1+2 校验首选未选、物理历史同选、再选不足/超量/重复等，合法组合 12 种；3+3 校验重复、不足 3 门、超 3 门。每类错误有独立错误码。面试时需如实说明：完整校验矩阵在 PRD 中定义，源码里 API 层做了 subjectType 枚举校验、前端做了基础校验，**完整矩阵尚未全部编码进后端**。

**Q6：项目最难的部分是什么？**
数据工程。源数据是各种格式的 Markdown，需要写解析器清洗成结构化记录，还要处理省份编码、选科要求、批次口径差异。约 32KB 的 `markdownParsers.ts` 和 8 个导入脚本是这块的主要产出。QA 时发现 `subject_coverages.province_code` 全为 NULL、没有省份差异，就是导入环节的问题，后来修掉了。

**Q7：QPS / 并发这些数据怎么来的？**
架构文档做过流量模型推演（如峰值 QPS ≥10000、出分日 895 万请求），这些是**容量规划的设计目标，不是实测结果**。项目没有做过高并发压测，被问到要如实说明。当前实现是单 Express 进程 + Repository 模式，Redis 缓存、限流熔断、读写分离都在设计文档中但未编码。

**Q8：有没有做测试？**
后端认证链路有 Vitest + Supertest 的自动化测试；数据侧有核对脚本；另做了两轮 QA 回归，第一轮 FAIL、第二轮 PASS。没有端到端 UI 自动化测试，UI 以手动验证 + 截图记录为主。

## 4. 面试诚实清单（务必记住）

说这些会加分，因为真实且经得起追问：

- 承认「架构文档里的 Redis / 限流 / 微服务是设计目标，没有落地」。
- 承认「数据覆盖是样本规模（114/172/11 条），不是全 31 省全量」。
- 承认「没有做高并发压测，QPS 是估算」。
- 承认「选科完整校验矩阵在 PRD 里，代码只实现了基础校验」。

被追问时，把话题接回「为什么当时这么取舍」——例如「两人团队优先保证主链路跑通，把缓存和限流后置」，这是工程判断，不是缺陷。
